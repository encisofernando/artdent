# Handoff — 2026-08-26

## 1. Trabajos con fases marcados "Entregado"/"Listo" a mano nunca facturaban

El usuario reportó que ORD-00500 (BASSI FABIAN, $260.000) apareció como
"Entregado" en la lista de Órdenes pero no generó deuda en su cuenta
corriente. Investigado con la lógica real de facturación:

- ORD-00500 tiene una sola fase (ENCERADO, $15.000) que **nunca pasó por
  el Kiosk** — quedó en estado `pending`, nunca se inició/mandó a
  prueba/completó.
- Su historial de estados salta directo de `ready` a `delivered` con la
  nota genérica "Estado actualizado a: delivered" — es decir, alguien usó
  la pantalla de **Editar Trabajo** (no el Kiosk) y cambió el desplegable
  de estado a "Entregado" a mano.
- `JobController::update()` (y `store()`) permiten fijar el campo
  `status` libremente a cualquier valor, incluido `delivered`. Ninguno de
  los dos dispara la facturación por fases — por diseño, desde el fix del
  5-6/8, esa responsabilidad es 100% de `JobPhaseService`
  (`billPhaseIfNeeded()`/`settleArancelRemainder()`, llamadas solo desde
  `completePhase()`/`sendToProof()` en el Kiosk). Si un trabajo nunca pasa
  por ahí, nada lo factura, sin importar qué estado tenga.

**Barrido en producción**: se encontraron **17 órdenes en total** con este
mismo patrón (status `ready`/`delivered`, fases nunca completadas, $0
facturado), incluyendo ORD-00500:

```
ORD-00426, ORD-00427, ORD-00441, ORD-00445, ORD-00455, ORD-00456,
ORD-00468, ORD-00472, ORD-00473, ORD-00475, ORD-00478, ORD-00482,
ORD-00494, ORD-00495, ORD-00496, ORD-00497, ORD-00500
```

Con confirmación explícita del usuario, se facturaron las 17 usando la
lógica real del sistema (invocada por reflection, no reimplementada):
`JobPhaseService::billPhaseIfNeeded()` por cada fase + `settleArancelRemainder()`
para cerrar contra `job.total`. Verificado que cada orden quedó facturada
exactamente por su total (ver script `bill_backlog.php` en el handoff de
esta sesión). Balances de cuenta recalculados por las dudas — coincidieron
con lo que `applyMove()` ya había dejado, sin drift.

**Corrección posterior**: el backfill usó `Carbon::today()` como
`move_date` (fecha en que corrí el script), no la fecha real en que se
cargó cada orden. El usuario lo notó al ver todo con fecha 26/8 en Cuentas
Corrientes. Se corrigió `move_date` de los 34 movimientos (17 órdenes ×
fase + remanente) para que sea el `received_at` real de cada trabajo — el
saldo total de cada cuenta no cambia, solo la fecha mostrada en el
historial.

**Se encontraron también 3 órdenes con el problema opuesto** (doble
cobro histórico: ORD-00305, ORD-00314, ORD-00354) — tienen un cargo viejo
`Job::class` por el total completo (mecanismo pre-5/8) *más* un cargo
`JobPhaseProgress::class` por el mismo total (el bug de "última fase =
remanente" que se sacó el 6/8). El usuario decidió **dejarlas como
están** — mismo criterio que las órdenes de julio en la limpieza
anterior, período cerrado.

### Fix de código: `billOutstandingForManualDelivery()`

Nuevo método público en `JobPhaseService`:

```php
public function billOutstandingForManualDelivery(Job $job): void
{
    $job->loadMissing('phaseProgress.tariffPhase');
    if ($job->phaseProgress->isEmpty()) return;
    foreach ($job->phaseProgress as $phase) {
        $this->billPhaseIfNeeded($phase);
    }
    $this->settleArancelRemainder($job);
}
```

Llamado desde `JobController::store()` y `update()` (inyectado
`JobPhaseService` por constructor) **solo cuando `status === 'delivered'`**
en el request — si el trabajo tiene fases, se asegura de facturar
cualquier fase sin cobrar + el remanente antes de dejarlo como entregado,
exactamente igual que si hubiera pasado por el Kiosk. Reutiliza los
métodos privados existentes (mismo camino de código, mismo comportamiento,
imposible que cobre distinto a como lo haría `completePhase()`).

No se tocó el flujo normal del Kiosk (`sendToProof`/`completePhase`/
`registerDelivery`) — ese ya factura correctamente porque solo llega a
"ready"/"delivered" después de que las fases se completaron de verdad.

Desplegado a producción (`JobController.php`, `JobPhaseService.php`),
verificado con `php -l` antes y después de subir, cachés limpiadas
(`php artisan optimize:clear`).

**Nota para el futuro**: si se repite este patrón con trabajos que llegan
a `ready` (no `delivered`) sin pasar por el Kiosk, el fix actual no los
cubre hasta que alguien los marque `delivered` desde Editar Trabajo — no
se extendió a la transición a `ready` porque no fue parte de lo pedido en
esta sesión. Si vuelve a aparecer, revisar si conviene aplicar la misma
protección ahí también.
