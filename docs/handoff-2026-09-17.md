## 1. Contexto y Objetivos Cumplidos

En esta sesión se abordaron dos requerimientos principales:
1. **Módulo Completo de Stock, Movimientos y Reportes de Ventas/Rentabilidad**:
   - Corrección de bugs en relaciones de `StockMovement` (N+1 y referencias indefinidas en frontend).
   - Captura y persistencia de costo histórico (`cost_price_snapshot`) en cada venta para calcular márgenes reales sin distorsión por inflación.
   - Nueva página de analítica: **Ventas por Período** (`/reportes/ventas-por-periodo`) con gráficos de barras interactivos, comparativa con período anterior y ranking Top 10 productos.
   - Nueva página de **Valorización de Inventario** (`/stocks/valuation`) con KPIs a costo, unidades físicas y alertas de stock mínimo/quiebre.
   - Exportaciones en streaming CSV (UTF-8 con BOM y separador `;`) para Stock Actual, Movimientos de Stock y Ventas por Período.
   - Reestructuración del Hub central de `/reportes`.
2. **Aislamiento de Módulos según Plan del Tenant (Caso Plan Starter)**:
   - Detección de secciones visibles indebidamente en `/reportes` para tenants en plan `starter` (como `pos.artcode.com.ar`).
   - El plan `starter` solo contrata `clientes` y `reportes` (no incluye `laboratorio`, `insumos` ni `contabilidad`).
   - Se condicionó la interfaz de `/reportes`, `/settings` y `/ayuda` mediante `props.enabled_modules` (`hasModule()`).
   - Se blindaron las rutas backend de exportación de laboratorio (`/export/jobs`, `/export/dentists`, `/export/tariffs`) con el middleware `module:laboratorio`.
   - Se ajustó el chatbot Artie (`ChatbotService`) para requerir el módulo `chat_ia` y adaptar su saludo inicial eliminando menciones a laboratorio cuando el tenant no lo posee.

## 4. Proceso Exacto de Deploy (Playbook Canónico)

El VPS **NO** utiliza `git pull` de forma directa. Todo el ciclo de release se gestiona desde el monorepo local `/home/infranet/Documentos/Proyectos/artdent` (`artdent-crm/`) sincronizando archivos mediante `rsync` con checksum y ejecutando tareas vía SSH.

### Paso 1: Pruebas Locales, Linter y Git Push
```bash
# 1. Ejecutar Pint para asegurar formato PSR-12 / Laravel
vendor/bin/pint --dirty

# 2. Commit en monorepo
git add -A
git commit -m "tipo(alcance): descripción del cambio"

# 3. Push a origin (dispara el pre-push hook con 81 tests automatizados ~45-55s)
git push origin main
```

### Paso 2: Despliegue en `pos.artdent.com.ar` (multi_tenant, tenant `artdent` → `fer_artdent`)
```bash
# A. Backup de seguridad rápido del entorno
ssh donweb "cp /home/fer/web/pos.artdent.com.ar/public_html/.env /home/fer/backups/env-artdent-\$(date +%Y%m%d).bak"

# B. Sincronización de código (sin tocar vendor, node_modules, storage ni .env)
#    Incluye resources/views (PDFs/blades), config, bootstrap (sin cache) y lang: antes faltaban.
SITE=/home/fer/web/pos.artdent.com.ar/public_html
for d in app routes database config lang resources/js resources/views resources/css; do
  rsync -az --checksum artdent-crm/$d/ donweb:$SITE/$d/
done
rsync -az --checksum --exclude=cache/ artdent-crm/bootstrap/ donweb:$SITE/bootstrap/

# C. Service worker: SIEMPRE bumpear CACHE_VERSION en artdent-crm/public/sw.js si cambia el frontend.
#    Este sitio sirve la raíz public_html como DocumentRoot: nginx entrega cualquier archivo estático
#    que exista en la raíz ANTES de reescribir a public/. No debe existir public_html/sw.js
#    (había una copia vieja 2026-08-10-v4 tapando a public/sw.js; eliminada el 2026-09-30).
rsync -az --checksum artdent-crm/public/sw.js donweb:$SITE/public/sw.js

# D. Migraciones (si aplica)
ssh donweb "cd $SITE && php artisan migrate --force"
# Si la migración es específica de tenant:
# ssh donweb "cd $SITE && php artisan migrate --path=database/migrations/tenant/<archivo>.php --force"

# E. Compilación de assets y limpieza de caché
ssh donweb "cd $SITE && npm run build && php artisan optimize:clear"
```

### Paso 3: Despliegue en `pos.artcode.com.ar` (Multitenant)
```bash
# A. Sincronización de código al directorio private/app (mismas carpetas que el Paso 2)
APP=/home/artcode/web/pos.artcode.com.ar/private/app
PUB=/home/artcode/web/pos.artcode.com.ar/public_html
for d in app routes database config lang resources/js resources/views resources/css; do
  rsync -az --checksum artdent-crm/$d/ donweb:$APP/$d/
done
rsync -az --checksum --exclude=cache/ artdent-crm/bootstrap/ donweb:$APP/bootstrap/

# B. Service worker: acá el DocumentRoot es public_html/ (separado del código), va directo ahí
rsync -az --checksum artdent-crm/public/sw.js donweb:$PUB/sw.js

# C. Migración de bases de datos tenant (para todos los inquilinos)
ssh donweb "cd $APP && php artisan tenants:migrate --force"

# D. Compilación de assets Vite, sincronización a public_html y limpieza de caché
ssh donweb "cd $APP && npm run build && rsync -a --checksum $APP/public/build/ $PUB/build/ && php artisan optimize:clear"
```

### Paso 4: Health Check y Verificación Final
```bash
ssh donweb "curl -s -o /dev/null -w '%{http_code}' https://pos.artdent.com.ar/login && echo '' && curl -s -o /dev/null -w '%{http_code}' https://pos.artcode.com.ar/login && echo ''"
```

### Aclaraciones sobre el playbook de la sección 4
- **Build en el servidor (`npm run build` por SSH) es válido.** El `.env` de producción no define
  `VITE_REVERB_FORCE_LOCAL`, así que queda en false; el bundle de pos.artcode apunta a `ws.artcode.com.ar`.
  La regla de "compilar con `VITE_REVERB_FORCE_LOCAL=false`" aplica **solo si se compila en local**
  (el `.env` local lo tiene en `true`).
- Los archivos de `public/build` quedaron con owner `root` (el build se corrió como root). Funciona,
  pero conviene compilar con el usuario del sitio para no arrastrar problemas de permisos.
- **`CACHE_VERSION` de `public/sw.js` no se bumpeó** en los deploys del 16-17/09 (seguía en
  `2026-08-16-v2`). Además, **pos.artdent.com.ar servía un `sw.js` todavía más viejo
  (`2026-08-10-v4`)**: había una copia suelta en la raíz `public_html/sw.js` que nginx entregaba
  antes de reescribir a `public/` (`try_files $uri @fallback`). Corregido: CACHE_VERSION →
  `2026-09-30-v1`, se eliminó la copia de la raíz y el playbook (sección 4) ahora sincroniza `sw.js`
  y verifica la versión servida. `.htaccess` y `storage` en esa raíz son legítimos y no se tocan.
- El playbook no sincronizaba `config/`, `bootstrap/`, `resources/views/`, `resources/css/` ni `lang/`
  (por ej. `5de94a9` modificó `resources/views/pdf/invoice_afip.blade.php`). Al 30/09 esas carpetas
  coincidían con `main` en ambos sitios; la sección 4 ya las incluye.
- El pre-push hook existe en `.githooks/pre-push` (activo vía `git config core.hooksPath`), no en `.git/hooks/`.
- La base `artcode_linedigital` (deploy de Line Digital, rama `linedigital-lab` en el repo `../linedigital`)
  **no** tiene `cost_price_snapshot`: esperable, esa rama todavía no incorporó los cambios de septiembre.

## 6. Reverb (tiempo real) en pos.artdent.com.ar — 2026-09-30

Estaba pendiente desde el 02/08 (`BROADCAST_CONNECTION=log`, sin `VITE_REVERB_*`).

**Decisión:** reusar la app de Reverb ya existente en vez de sumar una app nueva a `config/reverb.php`
(eso obligaba a reiniciar `reverb.service`, que sirve tráfico real de ArtCode). Es seguro porque:
- todos los canales llevan `tenant.{tenantId}` (o `ticket.{id}` validado contra el tenant) y los
  closures de `routes/channels.php` vuelven a resolver el tenant del lado del servidor;
- los ids de tenant son únicos en la central compartida (`artdent` ≠ `artcode-pos`, etc.);
- `allowed_origins` de la app es `['*']`.

**Cambios en producción:**
- `.env` de pos.artdent (backup: `/home/fer/backups/env-artdent-pre-reverb-20260930.bak`):
  `BROADCAST_CONNECTION=reverb` + `REVERB_APP_ID/KEY/SECRET/HOST/PORT/SCHEME` copiados del `.env`
  de pos.artcode + `VITE_REVERB_*` interpolando esas variables.
- `npm run build` en el servidor (el host se hornea en el bundle) + `optimize:clear`.
- `CACHE_VERSION` → `2026-09-30-v3` (desplegado en ambos sitios).
- No se creó queue worker: con `QUEUE_CONNECTION=sync` el broadcast es inline (~200 ms).

**Verificado:** broadcast server→Reverb OK; en Chrome headless contra `https://pos.artdent.com.ar/login`
Echo queda `connected` y un evento emitido por tinker en un canal público de diagnóstico llega al
navegador; `/broadcasting/auth` sin sesión → 401 (ruta viva, protegida); en web el tenant se resuelve
como `artdent` (`tenant.session`), que es el id que usan canales y Topbar.
**No verificado:** canales privados con sesión real (notificaciones, pedidos, QR Nave): requiere login.

**Limitación conocida (igual que en pos.artcode):** notificaciones creadas fuera de un request web
(cron, consola, webhooks sin tenancy inicializada) se emiten a `tenant.owner.notifications` y no
llegan en vivo; el Topbar las toma igual con el poll de respaldo de 120 s.

**Rollback:** restaurar el backup del `.env`, `npm run build` y `optimize:clear`.
