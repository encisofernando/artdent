# Handoff — 2026-08-04 (madrugada, continuación del 3/8)

Sigue a `docs/handoff-2026-08-03.md`. Esa sesión terminó con Google OAuth y el prefill del checkout confirmados; esta arrancó con "los puntos no serán monetarios" y se extendió mucho más de lo previsto. Todo lo de abajo está deployado y verificado en producción.

## 1. Fidelización dejó de ser monetaria — rediseño completo

Pedido del usuario: 1 punto ya no equivale a 1 peso. Se armó un catálogo de recompensas configurable (`LoyaltyReward`: nombre, puntos necesarios, descuento en pesos) desde el CRM → **Administración → Recompensas de Puntos**. POS y checkout ahora eligen una recompensa del catálogo en vez de escribir un monto libre.

- Puntos son enteros (`floor()`, no `round()`).
- `LoyaltyService::redeem()` reescrito: recibe un `LoyaltyReward`, debita puntos, devuelve el descuento en pesos. Nuevo `validateRedemption()` centraliza saldo + tope (`max_redemption_percentage`) para POS y checkout.
- Saldos viejos (5 cuentas, $29.730 bajo el modelo 1:1) se **resetearon a 0** en producción — confirmado explícitamente con el usuario, la función nunca se había anunciado a clientes.
- **Estado post-deploy**: `loyalty_settings.is_enabled=true` sigue activo, pero no había ninguna `LoyaltyReward` cargada al cierre de la sesión anterior — el usuario cargó una de prueba ("$2.000 de descuento", 200 pts) para probar el flujo.

Detalle completo: memoria `project_loyalty_non_monetary_rewards`.

## 2. Envío gratis a partir de un monto

Nuevo panel **Administración → Envío Gratis** (`ShippingSetting`: habilitado + monto mínimo). Se evalúa sobre el total ya con cupón y puntos aplicados, aplica a domicilio y moto (retiro ya era gratis siempre). Memoria: `project_free_shipping_threshold`.

## 3. Seguridad: costo de envío ya no confía en el cliente

De paso se encontró que `CatalogController::checkout()` tomaba el `shipping_cost` tal cual lo mandaba el navegador — cualquiera podía mandar 0 sin cobrar envío. Se recalcula 100% server-side contra Andreani (domicilio/sucursal) o el precio real de `ShippingMotoCompany` (moto). Mismo commit que el hallazgo de "Ingresos y Egresos".

## 4. Retiro en Sucursal de Andreani — feature nueva

Nunca había existido (`AndreaniService::endpoint('sucursales')` estaba definido pero sin usar). Se agregó como cuarto método de envío:

- La misma cotización de Andreani (`cotizar()`) ya devuelve un rate `"sucursal"` (más barato que domicilio) — no hizo falta llamada extra a Andreani para el precio, solo para el listado de sucursales.
- Modal con buscador (`AndreaniBranchModal.tsx`) — **sin mapa**, la API de sucursales de Andreani no devuelve coordenadas, solo texto de dirección (confirmado contra la cuenta real).
- Nueva columna `ecommerce_orders.andreani_branch_code`.
- **Pendiente, fuera de alcance**: `AndreaniService::crearOrdenParaPedido()` (arma el envío real cuando se confirma un pedido pago) todavía asume domicilio — no soporta armar el envío real a una sucursal todavía. El pedido se cobra y guarda bien, pero la etiqueta/retiro real con Andreani para `andreani_branch` no está conectada.
- **Los otros 2 contratos de la cuenta** ("llega hoy", "bigger") no aparecen en ninguna cotización probada (chico/grande, Formosa/CABA) — probablemente la API de WooCommerce de Andreani que usamos no los expone. El usuario decidió esperar a confirmar con Andreani antes de seguir investigando.

Detalle completo + los 3 fixes en vivo que salieron después (ver abajo): memoria `project_andreani_branch_pickup`.

## 5. Fixes en vivo sobre la feature de sucursal (probado en el momento)

1. **Sucursal pisaba la dirección de domicilio**: `selectBranch()` escribía en el mismo estado (`address`/`city`/`province`) que "Envío a domicilio" — al volver a domicilio quedaba la dirección de la sucursal pegada. Corregido, cada método arma su propia dirección en el payload sin pisar estado compartido.
2. **Faltaba el campo de código postal para sucursal**: al agregar la feature me olvidé de mostrar un input de CP fuera de "Envío a domicilio" — ni invitados ni clientes logueados podían verlo/editarlo para esa opción.
3. **A pedido del usuario**: se sacaron Ciudad/Provincia del checkout (Andreani no las usa para nada, solo el CP) y se dejó un único input de Código Postal arriba del selector de método, sacando también los dos que habían quedado duplicados.

**Ojo pendiente**: la disponibilidad de "Moto Mandados" en el backend sigue mirando si `city`/`province` contiene "formosa" — ese estado ya no tiene input visible, solo se llena vía prefill (dirección guardada / `Customer.city`). Funciona para clientes logueados con datos cargados; un invitado sin cuenta ya no puede escribirlo a mano. Si se reporta que Moto no aparece disponible para invitados, la causa es esta — habría que migrar esa detección a código postal.

## 6. Fix: build de producción del CRM con Reverb apuntando a localhost

Los builds del CRM subidos durante el 3/8 se compilaron con el `.env` local, que tiene `VITE_REVERB_FORCE_LOCAL=true` (pensado para dev) — quedó horneado en el bundle, haciendo que cada página logueada intentara conectar a `wss://localhost:8080` en loop (solo ruido de consola, sin impacto funcional). Corregido recompilando con `VITE_REVERB_FORCE_LOCAL=false npm run build` explícito. **Cualquier build futuro del CRM tiene que usar ese override** — ver memoria `feedback_reverb_force_local_build`.

## 7. Bugs sueltos encontrados y corregidos

- **Miniatura rota de "PACK X1 25MM COMPOSTELA"**: 1 de 197 imágenes de producto tenía `thumb_url` seteado en la DB pero el archivo real nunca se guardó (caso aislado, no un problema del flujo de subida — se verificó que las otras 196 están bien). Regenerada desde la imagen completa.
- **Header pegajoso del modal "Cuotas Nave"**: usaba un hack de márgenes negativos que dejaba una fila de contenido asomando por encima del título al hacer scroll. Corregido con el patrón estándar (header con su propio padding/fondo opaco/z-index, separado del contenido).

## 8. Cambio de topología de red del consultorio + impresora térmica LAN configurada

Sesión separada de la de arriba (esta trabajó Hikvision/ISUP los días previos,
no loyalty/shipping). Dos cosas importantes:

**El TP-Link pasó a modo Access Point.** En algún momento después de la
sesión de diagnóstico WiFi del 3/8, el usuario cambió el "Modo de trabajo"
del router TP-Link de "Router Inalámbrico Estándar" a **"Punto de Acceso"**.
Esto significa que el TP-Link **ya no hace NAT/DHCP propio** — ahora es sólo
switch + WiFi bridge, y todo (cable y WiFi, red `ArtDent Digital`) cuelga
directo del router de Starlink, que pasó a ser el único DHCP/gateway de toda
la red. **Consecuencia: la subred `192.168.0.0/24` que se usaba para el
Hikvision, la reserva DHCP, el port forwarding del puerto 8899, etc. ya no
existe** — todo el consultorio ahora vive en `192.168.1.0/24` (rango del
router de Starlink). Si una futura sesión ve que el Hikvision/Tailscale/DDNS
de `docs/artdent-ddns-portforwarding.md` no anda, **esta es probablemente la
causa** — hay que verificar la IP actual del terminal en la nueva subred y
si hace falta rehacer la reserva DHCP en el router de Starlink (sigue sin
confirmarse si ese router expone esa opción).

**Impresora térmica 3nStar RPT006S configurada por LAN en la app Android.**
El usuario conectó la impresora por cable al TP-Link. Traía de fábrica una
IP fija fuera de rango (`192.168.123.100/24`, DHCP deshabilitado) — típico
default de estos módulos Xprinter/3nStar. Se activó DHCP desde su panel web
propio y quedó con `192.168.1.62` (asignada por el router de Starlink, sin
reserva — puede cambiar si el router reinicia).

Notas útiles para el futuro:
- **El "autotest" físico de este modelo (apagar → mantener FEED → encender)
  en realidad resetea la impresora a valores de fábrica**, no es un simple
  test — volvió a `192.168.123.100`/DHCP-off cada vez que se usó para
  "verificar" la IP actual. No usar ese combo para chequear estado; mejor
  escanear la red (puerto 9100 abierto = impresora) o mirar su panel web
  mientras esté en una IP conocida.
- La tablet donde corre la app (`com.artdent.crm`, Capacitor) estaba
  conectada por USB con depuración habilitada — para configurar una IP
  estática temporal (necesaria para hablarle a la impresora en su subred de
  fábrica antes de cambiarla) hubo que hacerlo a mano desde
  Ajustes → WiFi → editar red, porque ni `adb shell ip addr add` (sin
  permiso, `rtnetlink: Permission denied`, tablet no rooteada) ni la opción
  de la propia UI cedían fácil la primera vez.
- **La app corre en modo kiosco fijo** (`capacitor.config.json` tiene
  `server.url` hardcodeado a `/job-kiosk`, ver `artdent-android/`) — no hay
  forma de navegar a Configuración desde la UI. Para cargar la config de la
  impresora (`localStorage` keys `artdent_printer_lan` /
  `artdent_printer_transport`, ver `nativePrinter.js`) sin salir del kiosco,
  se usó el **debugger remoto de WebView vía ADB**: `adb shell cat
  /proc/net/unix | grep webview` para encontrar el socket
  `webview_devtools_remote_<pid>`, `adb forward tcp:PORT
  localabstract:webview_devtools_remote_<pid>`, `curl
  http://localhost:PORT/json` para el `webSocketDebuggerUrl`, y un script
  Node con `WebSocket` nativo (Node 22+) mandando `Runtime.evaluate` para
  ejecutar `localStorage.setItem(...)` directo en el contexto de la página.
  **Método reutilizable para cualquier cambio de `localStorage` en esta
  tablet sin salir del kiosco** — no hizo falta rebuildear la app ni tocar
  código nativo.
